System Design · Round-1 Pattern · RAG

Design a RAG System

Retrieval-Augmented Generation: given a private corpus (docs, wikis, code, tickets), answer natural-language questions with grounded, cited responses. Follow the NG round-1 skeleton: requirements → estimates → architecture → one deep dive. The deep dive here is the vector index — HNSW (Hierarchical Navigable Small World; often mistyped "HSWN") — because it's the component with the most interesting trade-offs.

01Requirements — say these first, then confirm

Scope the corpus and the query pattern before drawing anything. "Is this over a fixed document set or a living one? Do answers need citations? What's the latency budget?" — three questions that change the whole design.

Functional

  • Ingest: connect sources (files, wiki, code, DB), parse → chunk → embed → index. Continuous, not one-shot: docs change.
  • Query: NL question → retrieve relevant chunks → generate a grounded answer with citations back to source.
  • Freshness: an edited doc is reflected in answers within minutes (define SLA — this drives the whole ingest design).
  • Access control: a user only retrieves chunks they're allowed to read. Filter at retrieval, never after generation.
  • Feedback: thumbs up/down and "wrong source" reports feed an eval set.

Non-functional

  • Latency: p95 time-to-first-token ≤ ~1.5 s; retrieval itself ≤ 200 ms of that budget.
  • Quality: recall@k is the retrieval metric that caps everything downstream — a fact not retrieved cannot be answered. Target recall@8 ≥ 90% on an eval set.
  • Groundedness: no claim without a retrieved supporting chunk; hallucination is a correctness bug, not a style issue.
  • Cost: LLM tokens dominate; retrieval exists partly to keep prompts small.
  • Scale: corpus grows 10× without re-architecture; index rebuilds can't cause downtime.

The conclusion to say out loud: 200 GB of vectors doesn't fit one node's RAM comfortably → either quantize (int8/PQ), shard the index, or go disk-based (DiskANN). At 60 QPS with 30 ms ANN search a few replicas suffice — retrieval is not the bottleneck, ingest throughput and LLM cost are. Embedding 50 M chunks at ~1 ms/chunk on GPU batch ≈ 14 GPU-hours per full re-embed: fine occasionally, painful daily — hence incremental indexing.

03High-level architecture

Two planes joined by shared storage: an offline ingestion plane (throughput-optimized, async, retryable) and an online query plane (latency-optimized). They scale, fail, and deploy independently — say that sentence; it's the design's thesis.

Offline · Ingestion plane
Shared storage & indexes
Online · Query plane (≤1.5 s)

Sources & connectors

Wiki, Drive, git, tickets, DB dumps. Webhooks/CDC for change events; periodic crawl as reconciliation backstop.

Message queue (Kafka/SQS)

Decouples burst crawl from GPU embed. Retry + DLQ; per-doc idempotency key doc_id@version so replays don't duplicate.

Parser / normalizer

PDF/HTML → text, table extraction, dedupe, PII scrub. The quality ceiling lives here — garbage chunks poison every stage downstream.

Chunker

Structure-aware (headings, code blocks) > fixed-size. 300–800 tokens, 10–20% overlap; store parent-doc pointer for context expansion.

Embedder (GPU batch)

Batched, throughput-optimized. Embedding model version pinned per index — query and corpus must share vector space.

Index writer

Upserts to vector + keyword + metadata stores transactionally per chunk batch; deletes are tombstoned, compacted off-peak.

Re-embed / refresh worker

On embedding-model upgrade: build index v2 side-by-side, shadow-test recall, flip alias — never mutate the live index in place.

Eval harness (offline)

Golden Q→chunk set; every chunker/embedder/index change gets recall@k regression-tested before rollout. Feedback loop lands here.

Vector index — HNSW ★

ANN top-k in ~ms. The deep-dive component — see §06. Params M / efSearch are the recall-vs-latency knob.

Keyword index (BM25)

Exact tokens: IDs, error codes, function names — everything embeddings blur. Hybrid = vector ∪ BM25.

Metadata / chunk store

Chunk text, source URI, ACL tags, timestamps, doc version. Retrieval filters ACL inside the index query, not after.

Caches

Embedding cache (query string → vector) and semantic answer cache (similar-enough query → cached answer, short TTL).

Object store (raw docs)

Originals kept immutable — reprocessing is replay from source of truth, same artifact discipline as CI/CD.

Client + API gateway

Auth, rate limit, streaming response channel (SSE/WebSocket).

Query understanding

Rewrite follow-ups into standalone queries (cheap LLM), optional decomposition; embed the query (20 ms, cache hit ~40%).

Hybrid retrieval

Vector top-50 + BM25 top-50 in parallel → merge with RRF (reciprocal rank fusion — no score calibration needed) → ~top-50, ACL-filtered.

Reranker (cross-encoder)

Scores (query, chunk) jointly — far more accurate than bi-encoder cosine. 50 → top-8. ~120 ms. The single biggest quality lever after chunking.

Context assembly

Dedupe near-identical chunks, expand to parent section if budget allows, order stable, attach citation map chunk→URI.

LLM generation (streamed)

Grounding prompt: "answer only from context, cite chunk ids, say 'not found' when absent." Stream tokens; TTFT dominates UX.

Groundedness check

Cheap verifier: every claim maps to a cited chunk? On failure → regenerate once or degrade to "closest sources" list.

Feedback + telemetry

Thumbs, "wrong source", retrieval traces → eval set (dashed amber loop back to the offline harness).

06Deep dive — HNSW (Hierarchical Navigable Small World)

The standard in-memory ANN index (FAISS, Milvus, Qdrant, pgvector all ship it). One sentence: a skip list crossed with a proximity graph — sparse top layers with long-range links act as express lanes, the dense bottom layer holds every vector, and search greedily descends. Note the spelling: H-N-S-W.

Greedy descent: start at the entry point on the top layer, hop to whichever neighbor is closer to the query, and when no neighbor improves, drop one layer and repeat. Top layers cover distance in a few long hops (the skip-list trick); layer 0 does the fine-grained final search with beam width efSearch. Total hops ≈ O(log N).

  • M — max links per node per layer (~16–48). Higher M = denser graph = better recall & more RAM (each link is 4–8 bytes × 50 M nodes — this is where the 1.3–1.5× memory overhead comes from).
  • efConstruction — candidate-list width while building (~100–400). Higher = better graph quality, slower build. Pay once at index time.
  • efSearch — candidate-list (beam) width while querying. The live knob: raise it and recall climbs toward exact search while latency grows roughly linearly. Tune it against the eval set, per traffic class.
  • Insert = draw a random top level from an exponential distribution (most nodes exist only in layer 0 — that's what keeps upper layers sparse), greedy-search down to that level, connect the M nearest, prune diverse neighbors. Incremental — no retraining, unlike IVF whose centroids go stale.
  • Weaknesses to volunteer: RAM-resident by design; deletes are tombstones + periodic rebuild (graph edges can't be cheaply repaired); build is slower than IVF; recall degrades if the corpus distribution shifts hard and the graph was never rebuilt.
  • Why "small world": Milgram's six-degrees experiments + Kleinberg's result — greedy routing finds short paths only when a few long-range links exist among mostly short ones. HNSW engineers exactly that topology, then adds the hierarchy so the entry point is never far.

Spoken · 60s if asked "what is HNSW?"

"HNSW is the standard in-memory approximate-nearest-neighbor index — think of it as a skip list crossed with a proximity graph. Every vector is a node in layer zero with links to its near neighbors; a random minority of nodes also appear in sparser upper layers whose links span long distances. A query enters at the top, greedily hops to whichever neighbor is closer, and drops a layer whenever it can't improve — long hops first, fine hops last, about log-N total. Three parameters matter: M, the links per node, sets the memory-recall trade-off; efConstruction sets build quality; and efSearch is the runtime knob — widen the search beam and recall approaches exact search at the cost of latency. It gives ninety-five-plus percent recall in milliseconds and supports incremental inserts without retraining, which is why we chose it; the price is that the whole graph lives in RAM and deletes are tombstoned. If the corpus outgrew memory I'd move to quantization or DiskANN and re-validate recall on our eval set."

Spoken · 30s opener for the whole design

"I'd split RAG into an offline ingestion plane and an online query plane joined by three stores — a vector index, a keyword index, and a chunk-metadata store. Offline is throughput-shaped: parse, chunk structure-aware, embed in GPU batches, upsert idempotently. Online is latency-shaped: rewrite and embed the query, hybrid-retrieve fifty candidates from HNSW plus BM25, fuse with reciprocal rank fusion, cross-encoder rerank to eight, and generate with mandatory citations. Retrieval recall caps everything downstream, so an offline eval set with recall-at-k regression gates every change — the same discipline as my benchmark pipeline at Microsoft: verifiable ground truth first, then iterate."

07Bottlenecks & evolution — name these before they're asked

What breaks first

  • Parser quality — one bad PDF pipeline poisons thousands of chunks silently; detect via chunk-quality sampling.
  • Embedding model upgrade — full re-embed + side-by-side index swap; never mix vector spaces in one index.
  • ACL at scale — post-filtering can return <k results ("filtered-out starvation"); needs filter-aware ANN search.
  • Semantic cache staleness — doc updated but cached answer survives; invalidate by source-doc id, keep TTL short.
  • HNSW delete debt — heavy churn degrades the graph; schedule compaction/rebuild like any LSM-ish system.

10× evolution

  • 500 M chunks → shard HNSW by tenant/namespace, or move cold shards to DiskANN; router fans out + merges.
  • Quality plateau → fine-tune embeddings on click/feedback pairs; add query classification (navigational vs synthesis).
  • Multi-hop questions → agentic retrieval: decompose, retrieve per sub-question, iterate — my HDMAS wide-search experience is exactly this shape.
  • Cost pressure → route easy queries to a small model; cache aggressively; the LLM bill dwarfs the retrieval bill.
