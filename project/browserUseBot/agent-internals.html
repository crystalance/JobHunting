BrowserUseBot — Inside the Agent

How the browser-use engine actually runs a task, and what the harness adds around it: the perceive→decide→act step loop, a two-tier tool registry where reliability lives in code instead of prompts, and a layered memory design that keeps the context window flat while the durable state (dedup ledger, collected records, cookies) lives on disk.

BrowserAgentRunner — the harness entry point

run_task(goal, policy) / run_harvest(spec) → Result. Per run it assembles: a fresh Handoff(policy) · build_tools(store, ledger, handoff) · a BrowserSession on the persistent profile · the LLM wrapped in a Langfuse tracing proxy. Requests arrive here from the intent router (sheet A-01); everything below is one task's lifetime.

01Perceive

Browser state summary: an indexed DOM tree — every clickable becomes [N] the LLM can reference. URL, tabs, page info. Screenshot only when vision is on (harness skips capture otherwise).

02Assemble

MessageManager builds the prompt: system + task brief + step history + fresh state, compacted to fit the window. Bulky tool results are included only once, then dropped.

03Decide

One structured LLM call returns reflection and a batch of actions together — no separate planner. Several actions can run per step.

04Act

The Tools registry validates each action (pydantic), dispatches browser events → CDP commands. Harness tools run here too, right beside the defaults.

05Record

ActionResult + state → AgentHistory; tokens & latency logged as a Langfuse generation; the step lands in the replay transcript.

06Loop gate

Exit on the done action, the step budget (40 per task / 25 per chunk), or stop(). Otherwise: next step.

on_step_start hook

Runs BEFORE every step: policy allow-list check + login-wall detection. The one seam the harness needed — no fork. Internals ↓ bottom-right.

Harness tools — CodeAct + guarantees

run_jsagent writes one JS IIFE at runtime; bulk DOM work (all cards on a page) in a single call
extract_and_saveJS returns record(s) → persisted straight to the store; atomic, deduped by note-id, nothing re-typed
discover_candidatesJS returns {title, href}[] → queued in the durable ledger (full xsec_token URLs)
open_searchnavigates straight to the results-page URL — never fights the on-page search box
open_next_postharness picks and opens the next queued URL; the model never types or guesses one
save_items / save_candidatesJSON-array fallbacks; a __FROM_RUN_JS__ sentinel is backfilled from the last run_js result so placeholders can't corrupt data
request_loginthe LLM judges a login wall is blocking it → human handoff, resumes on the authenticated page

How they bind

Each tool's pydantic param model becomes a JSON schema auto-published to the LLM; the description steers when to use it. Prompts request, tools guarantee — dedup, queue, real URLs, and login live in code the model cannot corrupt.

BrowserSession + CDP (browser-use)

Event-driven session with watchdogs (crash · screenshot · security · downloads) and the actor layer (Page / Element / Mouse). Builds the indexed DOM the loop perceives. Persistent user-data-dir profile keeps cookies; keep_alive=True lets ONE warm browser serve many Agent runs — the chunk loop reuses it.

Memory — layered; durable state lives outside the context window
L0 · IN-CONTEXT

Working memory

AgentOutput.memory + next_goal — a scratchpad the model rewrites every step. Cheapest, most volatile layer.

L1 · IN-CONTEXT

Step history

MessageManager carries prior steps and compacts to fit the window. Big tool outputs are shown once (include_extracted_content_only_once) then dropped.

L2 · CONTEXT BOUNDARY

Chunk reset

BatchCrawl discards the context every ~25 steps. The fresh agent gets a counts-only brief (saved 37/60 · pending 12) — never the item list. Context stays flat at any crawl size.

L3 · ON DISK

Collected store

Append-only raw.jsonl of full records (whole 正文 body, exact URLs). Read later by the synthesizer — it never re-enters the agent loop.

L4 · ON DISK · DURABLE

Visited ledger

SQLite per company/scope: visited (dedup + resume) and candidates (URL queue). Dedup enforced in code, not prompt — hundreds of posts, zero context growth.

L5 · CROSS-RUN

Profile · skills · replay

Cookies persist → logins are rare. Markdown skills = procedural memory prepended to matching tasks. Transcripts (full history JSON) + RunStore records for replay and metrics.

Phase 2 — synthesis (browser-less)

After the loop: save_company_md organizes the records into 面经.md; for one-off tasks synthesize() writes the final answer from raw.jsonl — grounded only in collected records, links kept exactly. Gathering and answering are separate phases.

Integration: BatchCrawl is NOT a fork of browser-use. It is the same Agent class given (a) a task brief, (b) extra tools wired to the ledger + store, and (c) this outer while-loop. The engine never changed — that's why new capabilities stay cheap.

Login handoff — internals

Belt: the hook checks URL markers (login/signin/sso…) plus a universal DOM heuristic — a password field, or a visible modal whose text matches login keywords in 9 languages. Braces: the request_login tool lets the LLM hand off anything the heuristic misses. Pausing = awaiting an asyncio.Event between steps (browser stays alive, no busy loop); /done sets it and the same step resumes on the authenticated page. Allow-list breach → agent.stop(). One auto-handoff per task; agent-requested ones are always allowed.

Observability — per LLM call, not per run

A _TracedLLM proxy wraps ainvoke: every call becomes a Langfuse generation (model, last messages, tokens, latency, errors) — the router, every agent step, and the synthesizer are all visible separately. Trace id = request_id → deterministic deep link; chunks share a session id. Best-effort by design: a tracing failure can never break a task. Transcripts dump the full AgentHistory JSON for offline replay.

One step, end to end

Each step: read the page as an indexed DOM tree (element [23] = that button — no pixel guessing), assemble a bounded prompt, make one structured LLM call that returns reflection (thinking · evaluation · memory · next_goal) and a batch of actions, execute them through the registry, record everything. The done action or the step budget ends the run. The per-step hook is the only seam the harness adds — browser-use is reused, never forked.

Tools: prompts request, code guarantees

The CodeAct move: run_js collapses N element-actions into one snippet — a whole results page is harvested in a single LLM round-trip. The paired extract_and_save / discover_candidates make extraction atomic: the JS result is persisted by the harness, so the model can't lose data re-typing it (and the __FROM_RUN_JS__ sentinel backfill catches even lazy placeholders). Everything reliability-critical — dedup, queue, real URLs, login — is a tool, not an instruction the model can drift from.

Memory: the context window is a cache

Treat the LLM context as L0/L1 of a memory hierarchy; everything that must survive lives in SQLite, JSONL, and the browser profile. The chunk reset (L2) is the trick that makes 300-post crawls possible: the model only ever sees counts (saved 37/60 · pending 12), and the harness serves the next URL from the ledger. Dedup is a database constraint, not a plea in the prompt — so it cannot be hallucinated away.

The outer loop + handoff

BatchCrawl loops: counts-only brief → fresh agent (≤25 steps) on the same warm browser → gate (target reached, two no-progress chunks, empty queue, or 20-chunk ceiling) → Phase-2 synthesis. Login walls pause the loop from inside a step: a DOM heuristic or the model's own request_login call parks the agent on an asyncio.Event until you finish logging in and send /done — then the very same step continues, authenticated, cookies saved for next time.
