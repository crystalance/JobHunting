TikTok GA · JD: knowledge management across large codebases

Design an engineering knowledge base

Not “ChatGPT over Confluence.” A control-plane memory for humans and AI agents: the same retrieved context that answers “where is rate-limit enforced?” also feeds diagnosis, refactor, and CI fix agents. RAG is the retrieval kernel — enterprise pattern below — not the whole product. Pair with rag_system_design.html for HNSW / hybrid / rerank mechanics.

01Functional requirements — say these first, then confirm

Ask: which corpora? code-only or wiki+tickets+CI? agents as users or only humans? auto-apply patches or retrieve-and-cite? Confirm ACL: code is confidential.

Functional

  • Ingest living sources: git (file+PR+ADR), wiki/runbooks, tickets, CI logs / flaky history, CODEOWNERS, service catalog. Continuous, not a nightly dump.
  • Ask: NL question → grounded answer with citations (repo path + commit SHA, or ticket id). “Not found” is a valid answer.
  • Navigate: jump from a symbol / stack trace / failing test to owners, tests, last incidents, related ADRs.
  • Agent retrieve API: same ACL as humans; tool returns chunks + citations, not a hallucinated essay. First-class citizen of the platform (JD).
  • Write-back (optional v2): agent proposes a doc/code patch; lands only through CI + owners — KB does not auto-merge.
  • Eval: golden Q→chunk set; recall@k gates every embedder/chunker change. Same discipline as the Microsoft benchmark pipeline.

Non-functional

  • ACL at retrieval, never after generation. A leak of an internal service is an incident.
  • Freshness: merged PR reflected in index within minutes; wiki/ticket in ≤15 min.
  • Latency: interactive p95 TTFT ≤ 2s; agent-tool retrieve ≤ 200 ms of that (same budget as generic RAG).
  • Groundedness: no claim without a cited chunk. Hallucinated imports are correctness bugs.
  • Scale: 108–109 LOC class monorepo + years of tickets; index rebuilds without downtime.
  • Cost: LLM tokens dominate; retrieval exists to keep agent context small (task-local, not whole-repo).

02How enterprises actually use RAG

Interviewers hear “RAG” and picture a chatbot. Name the pattern first: retrieve-then-generate over private corpora, with citations and ACL. Then name the jobs companies actually buy.

1. Internal Q&A

HR, policy, onboarding wiki. Job: replace “ask in Slack.” Failure mode: stale page still ranks #1. Fix: ingest timestamps + recency in rank, expire chunks when the doc is archived.

2. Support / tickets

Manuals + past tickets. Job: draft a reply with links. Failure: citing another customer’s ticket. Fix: ACL + PII strip at ingest, not in the prompt.

3. Code copilot / “where is X”

This JD. Job: locate implementation, not write a novel. Hybrid: BM25 for FooService, vectors for “how do we retry payments.” Cite path@SHA.

4. Incident / on-call

Runbooks + similar pages + last postmortem. Job: shorten time-to-mitigate. Failure: retrieving the wrong service’s runbook. Fix: identity keys — service name, env, cluster — source-visible in the chunk (same lesson as your benchmark specs).

5. Compliance / legal

Contracts, policies. Job: extract clauses with audit trail. Highest ACL; often air-gapped index; human always in the loop.

6. What RAG is not

Not a replacement for tests, CI, or source of truth. RAG points at git/wiki. If wiki and code disagree, code+CI win; the answer should say both and flag drift.

Shared architecture every enterprise copy-pastes: connectors → parse/chunk → embed → vector + keyword indexes → query rewrite → hybrid retrieve → rerank → generate with citations. The product difference is corpus + ACL + freshness + eval, not a new neural net. For this team, add a second consumer: agents calling retrieve as a tool on the same indexes.

04Architecture — sources · RAG kernel · agent consumers

Thesis: one retrieval plane, many jobs. Maintenance / refactor / diagnosis / CI-opt are different planners that all call retrieve(query, filters, acl).

Sources (ingest)
RAG kernel
Consumers — humans + agents
Eval + policy

Git / monorepo

Files, blame, PRs, ADRs. Webhook on merge. Chunk by symbol / AST, not 512 naive tokens.

Wiki + runbooks

Structure-aware chunks; service name as identity key on every chunk.

Tickets / incidents

Resolved tickets + postmortems. PII scrub. Link to service + SHA.

CI / CD telemetry

Fail logs, flaky-test history, deploy SHAs. Powers “similar failure” retrieve.

Catalog + owners

CODEOWNERS, service dir, on-call. Not embedded — join at retrieve as filters.

Queue + workers

Idempotent doc@version. Re-embed only diffs. Dead-letter for parse fails.

Parse / chunk / enrich

Language parsers + markdown. Attach: repo, path, SHA, lang, owners, ACL tags, service.

Hybrid indexes

HNSW per corpus + BM25 + optional structural (SCIP/ctags). Filter ACL inside the query.

Retrieve API

retrieve(q, k, filters, principal) → chunks + scores + citations. Query rewrite for follow-ups. RRF + cross-encoder rerank.

Generate (optional)

Human chat: grounding prompt + citations. Agents often skip generate — they want chunks only in the tool result.

Freshness

File-level incremental. Wiki CDC. Nightly crawl as reconcile — same dual-path as your RAG SD.

Caches

Query-embed cache; short TTL semantic cache for human FAQ only — off for agent diagnosis (stale runbook kills).

Human: IDE / portal

“Where is X / how do we Y” — streamed answer, citations clickable to source@SHA.

Diagnosis / repair agent

Stack trace → retrieve similar incidents + owning service + tests. Patch in sandbox; CI is the judge.

Refactor / maintenance agent

Retrieve call graph + tests + ADR constraints. Incremental diffs (long-horizon harness: feature list, not one-shot).

CI optimization

Retrieve flaky history + impacted tests from the diff. Suggest quarantine / test-impact; never skip the deterministic gate.

Eval harness

Gold: “this question → these files.” Recall@8 ≥ 90%. Agent tasks: patch applies + tests (productivity / stability / correctness from JD line 12).

Policy

Least privilege on tools. Secrets never in chunks. Human approval above risk score. Audit log of every retrieve.

06Walk one diagnosis query

“Payment p99 spiked after deploy abc123 — what do we know?” Agent, not a chatbot essay.

  1. Auth the agent’s service account; ACL = that team’s services only.
  2. Router: intent = incident → query rewrite includes service name, SHA, “p99”, “payment”.
  3. Parallel retrieve: code (deploy diff files), runbooks (identity key = payment-svc), CI (that SHA’s jobs), tickets (similar alerts).
  4. Rerank; return top chunks with path@SHA / ticket ids. No generate unless a human opened chat.
  5. Repair agent uses chunks + sandbox + tests. KB logs the retrieve for eval (“did we surface the right runbook?”).
Spoken · 45s opener

I’d start from requirements: we need a living knowledge base over a large codebase that both developers and AI agents can query, with citations and ACL at retrieval time — not after the model speaks. Enterprises already use RAG as retrieve-then-generate over private wikis, tickets, and code; the standard shape is ingest, hybrid search, rerank, generate with sources. For this JD the twist is the consumers: diagnosis, refactor, and CI agents call the same retrieve API and get chunks, not a paragraph. Code is chunked by AST, indexes are split by corpus, freshness is webhook-driven, and we eval recall against a gold set the same way I gated benchmark facts. The knowledge base does not auto-merge; agents still go through CI. RAG is the kernel; the product is memory plus policy plus eval.

Don’t forget: ACL in the index query · cite path@SHA · agents ≠ chat · eval recall@k · code wins vs stale wiki. Full RAG knobs (HNSW, RRF, rerank): rag_system_design.html.
