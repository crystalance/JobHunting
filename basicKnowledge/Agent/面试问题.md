# Agent 面试题

口述口径。和 `systemdesign/enterprise_kb_agent.md` 对齐：线上是检索再生成，p95 看首 token；钱在生成，不在 18 QPS。

## 2. 如果上下文被截断了，你会优先怎么处理?

按「丢了会做错」的顺序留，从外往里砍。

先留系统约束和当前这句用户问题。硬规则（必须引用、不能越权、输出格式）被截掉，模型会照样往下说，而且说错。再留本轮工具结果和得分最高的那几段证据。历史对话从中间砍：老轮次压成几句摘要，最近一两轮留原文。RAG 的 chunk 先丢低分的，正在被引用的那段不丢。

还是超窗口，就少送 chunk（8 段收到 4 段），或者走一轮压缩，把旧工具输出收成结论。不要为了塞进窗口把引用规则删掉。

## 3. 大模型应用上线前你最关心哪些工程指标?

四组，每组一个数就能决定能不能上。

- 质量：检索 recall@k（有金标 chunk 才算），以及回答是否带得出处。任务成功率看的是「做成了」，引用率看的是「没瞎编」。
- 延迟：首 token 的 p95，加上端到端 p95。检索预算大约 50–150 ms，剩下的时间在生成。
- 成本：每次成功请求的输入 token、输出 token、模型调用次数。缓存命中率单列，因为它直接决定有多少请求根本没打到模型。
- 可靠和安全：错误率、超时、工具失败、步数打满的比例。越权必须是 0，不跟可用性做交换。

追踪里每条请求带上 prompt 版本、模型名、检索到的 chunk id，否则下面的回滚没有抓手。

## 4. 你怎么设计降级策略?

按代价从低到高撤，每一级都还给出一个真答案，或者明确说查不到。

1. 命中缓存就直接返回。
2. 关掉重排，省掉那 100 ms 和一份 GPU。
3. 简单问题走小模型。
4. 检索已经有高置信的原文时，返回摘录加引用，跳过生成。
5. 检索为空，就说查不到，并给文档入口。不让模型补。

超时和失败只在工具层重试一次。生成失败不再打进已经饱和的模型，否则高峰时重试会把队列堆死。降级开关按租户或按流量比例开，和正常路径用同一套追踪。

## 5. 如果成本超预算，先优化哪一层?

先优化生成这一层，而且先砍输入 token 和调用次数。一次 RAG 问答里，大约七到九成的推理费用在生成：系统提示加好几段 chunk 的预填充是大头，query embedding 只有几个百分点。

顺序是：能不调用就不调用（规则、缓存、高置信摘录）；然后把送进模型的 chunk 从 8 段收到 4 段；再把简单流量路由到小模型，难的才用大模型；最后才是前缀缓存。重建向量索引、换 PDF 解析器、加 GPU，都不解决这 30% 的账单。

## 6. 怎样做 Prompt / 模型 / 索引回滚?

三样都做成「指过去的名字」，回滚是改指针，不是重新发布。

- Prompt：模板有版本号，请求日志里记下这个版本。配置指回上一版即可，索引不用动。
- 模型：调用方写的是别名，别名背后才是具体模型。旧端点保持热，拨回去不用冷启动。
- 索引：写入新版本，查询仍走旧 alias。召回评估过了再切 alias。回滚就是把 alias 拨回上一版。chunk id 保持稳定，已经发出去的引用还解得开。不要在原地覆盖向量。

## 7. 提示词模板怎么构建的？上下文工程有啥实践经验？比如做过 To Do List 优化吗？为啥它能让模型更聚焦？

模板按块拼，每块有固定位置：系统约束、工具清单、带分隔符的检索证据、裁剪后的历史、用户问题。用户问题在证据后面再放一次。长上下文里模型对中间最不敏感，问题和结论放两头。

证据块只放正文、页码和 chunk id，不把整篇文档贴进去。每条请求记录模板版本，方便和回滚、评估对上。

To Do List 是让模型先把剩余步骤写成一个短清单，放进上下文；后面每一轮只推进未完成的那一条，做完就划掉。它更聚焦，是因为「现在做哪一步」变成了一句新鲜的、靠前的约束，模型不用从整段历史里自己找目标，也不容易把已经做完的工具再调一遍。

多 agent 里我用过的是同一件事的进程外版本：HDMAS 的黑板让每个 agent 看见别人已经认领的子任务，所以不会重复认。单 agent 的清单留在上下文里，黑板留在文件里，约束的都是「下一步做什么」。

## 8. 做过查询改写吗？多维度查询改写具体是啥？当改写需要用户补充信息时，交互和技术怎么实现？

多轮里用户说「它」「那个合同」，检索不能直接拿这句去嵌入。改写就是把当前问题和最近几轮收成一句可以独立检索的话，再拿去搜。

多维度是同一句问法拆成几路，一起搜再合并。关键词一路抓条款号、专有名词；语义一路抓改写后的意思；复杂问题再拆成子问题各搜一次；能从话里抽出年份、文档类型，就先做元数据过滤再做近邻。几路的 id 用倒数排名融合，再按权限滤掉。

缺信息时，改写这一步返回结构化结果：能不能搜、缺哪个槽、要问用户的那一句话。缺槽位就不检索，把这一句问题返回给用户。用户的回答写回会话，下一轮再改写、再搜。只问一次。再缺就用已经有的条件搜，并在回答里说明假设。技术上就是一次结构化输出的分支，循环停在这一步，而不是在改写上打转。

## RAG 检索中，数据如何进行向量索引？

离线做，不放在提问路径上。解析后按结构切块，每块有稳定的 chunk id、正文、页码、标题路径、权限。嵌入模型把正文变成向量，向量和 chunk id 写进 HNSW；正文留在 chunk 表里；关键词另写一份 BM25。三处用同一个 chunk id。

线上只做：把问题嵌入，近邻搜索拿出 id，用 id 回表取正文，再送给模型。索引里不放大段原文。

## 文本分块的长度一般是多少？如何权衡？

大约 300–800 token，重叠 10%–20%。按标题和段落切，不按固定字数硬切。

太短会把一条条款切成两块，两块各自都像无关的话。太长则一个向量里混了好几个主题，近邻会偏，送进提示词的 token 也变多。检索用小块保证准，送给模型时展开它的父段（一节，或三到五页）保证读得懂。块的开头带上标题路径，向量里才有「这是哪份合同的哪一节」。

## 为什么使用向量数据库？与 MySQL 的区别是什么？PostgreSQL 对 Agent 有什么提升？

向量检索要的是高维空间里的最近邻。MySQL 的 B+ 树服务等值和范围，没有这种索引，全表算余弦在数据量上来之后不可用。向量库（或带向量索引的库）提供的是 HNSW 这类近似近邻，再加上按租户、权限过滤。

PostgreSQL 加 pgvector 把 agent 真正要的几样放进同一个库：会话、权限、chunk 正文、向量。可以先用 SQL 滤掉无权的行，再在剩下的行上做近邻；引用 id 和消息日志用事务写在一起。流量在每秒几十以内时，这一套够用。索引体积或延迟撑不住，再把近邻拆到专用向量库，chunk 正文仍然留在原来的表里。

## 如何评估 RAG 的召回率？常用指标有哪些？

先有标注：一个问题对应若干个应该被检索到的 chunk id 或页码。没有这份标注，召回率就算不出来。

Recall@k 是金标里有多少落在前 k 名。配合看 Hit Rate（前 k 里至少中一个）、MRR（第一个命中排第几）、nDCG（排得靠前的命中更值钱）。上线门槛用 Recall@k，按文档类型分开看，长合同和 FAQ 不是同一个数。

上下文精度、忠实度衡量的是「送进模型的段落干不干净、回答有没有超出段落」。那是生成指标，不能拿来代替召回。

## 如何处理大模型输出死循环问题？兜底策略是什么？如何让模型生成更优内容？

循环外面加硬上限：最大步数、最大工具调用次数。两个更早的停止条件：同一个工具加同一组参数连续出现两次就停；流式输出里，末尾一段和前文已经出现过的片段重合，就停。

兜底是把已经生成的部分返回去，并说明停在了哪一步。不要用同一条提示自动再跑一轮大模型。工具超时只重试一次。

内容更好，靠的是证据和停止条件，不靠把温度调高。检索到的段落放进上下文，要求每个结论能对上 chunk id，对不上就说查不到。简单请求走小模型，只有检索分低或者上一步失败才升级到大模型。

## 如何检测输出重复率？有哪些方法？

在线检测，超了就截断，不等整段生成完。

精确重复：对输出做滑动窗口，末尾 30–50 个 token 的哈希如果在前文出现过，就是复读。工具循环：把工具名和参数规范化后计数，同一对出现两次即算重复。

近似重复：按句子看和前文的重叠比例，或者看末尾和前文的最长公共子串。阈值按业务定，日志里留下「因为重复而停」的比例，避免把正常的列表和引用误杀。离线评估再用整段的重复 n-gram 比例看一版提示词是不是更容易复读。

## 如何设计 Agent 架构支持工具可插拔扩展？原理是什么？

循环固定，工具放在注册表里。循环只有四步：组上下文、调用模型、如果返回的是工具调用就按名字分发、把结果写回上下文，直到模型给出最终回答或步数打满。

一个工具是三样东西：名字、JSON schema、处理函数。模型每轮只看见当前注册表生成的清单。新增工具是往注册表里加一项，循环和提示词骨架不动。未知名字直接返回错误，不让模型编一个结果。

进程内就是 `add_tool` / `remove_tool`。进程外用 MCP：宿主调用 `tools/list` 拿到 schema，调用 `tools/call` 执行。对循环来说，MCP 服务器仍然只是注册表里的几项。

## Agent 和大模型（LLM）的核心区别是什么？

大模型是一次生成：给定上下文，产出下一段 token。Agent 是包在模型外面的循环，自己持有状态、工具、记忆和停止条件。模型是这个循环里的一次调用。

没有循环、没有工具、停不下来，就只是一次补全。有了「调用工具、观察结果、再决定下一步」，才是 agent。框架提供的是这个循环怎么调度，模型提供的是每一步的判断。

## MCP（模型上下文协议）解决了什么问题？

它把「宿主」和「工具、数据」之间的连接收成一套 JSON-RPC。宿主用同一套方法发现工具、调用工具、读取资源。工具方实现一次 MCP，任何听得懂 MCP 的宿主都能用。

否则每接一个数据源，每个 agent 框架都要写一个适配器，工具数和框架数是乘积。MCP 管的是模型和外部能力怎么接。agent 和 agent 之间怎么对话是另一件事，那是 A2A，不要混在一个答案里。

## Skills 和 Function Call 的区别是什么？

Function call 是一次执行：模型输出工具名和参数，运行时调用对应函数，把结果写回上下文。它是循环里的那一步动作，schema 短，每轮都放在请求里。

Skill 是一份按需加载的说明书：什么时候用、步骤是什么、配套哪些脚本。模型判断用得上，才把这份说明读进上下文，真要执行时仍然通过 function call 或命令去跑。

区别是加载的东西不同。Function call 执行一个函数。Skill 把一段本来会撑爆每轮提示词的流程留在外面，用到才读。一个 skill 里面通常会包含多次 function call。
