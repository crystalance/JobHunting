# AI system
## LLM basic

1. 什么是 prefill?
    1. 是模型推理的第一个阶段：模型一次性处理你输入的整段 Prompt，并建立后续生成需要的 KV Cache。
2. 推理分为两阶段
    1. Prefill 阶段
        并行处理输入中的所有 token
        计算每一层的 Attention
        把每个 token 对应的 Key、Value 保存进 KV Cache
        通常计算量大，但 GPU 并行效率高
    2. Decode 阶段
        利用 KV Cache，每次生成一个新 token
        新 token 再被加入 KV Cache
        重复执行，直到答案结束
        通常受显存带宽和串行生成速度限制
2.. Q/K/V 为什么拆三个矩阵？为什么除以 dk？

    **口语版：**
    Q、K、V 本质上是给每个 token 三种不同的"角色投影"：Q 是"我在找什么"，K 是"我能被怎么找到"，V 是"我真正携带的信息"。拆成三个独立矩阵是为了让这三种角色解耦，各自有独立的表达空间。反过来想，如果共用一个矩阵，比如 Q 和 K 相同，注意力矩阵就变成对称的——A 关注 B 的程度必须等于 B 关注 A，这在语言里显然不合理；而且每个 token 对自己的打分会恒定偏高。
    除以根号 dk 是数值稳定性问题：两个 dk 维向量做点积，方差大约随 dk 线性增长。dk 一大，点积的值就很大，softmax 会进入饱和区——最大值几乎拿走全部概率，其他位置梯度趋近于零，训练就不稳定了。除以根号 dk 正好把方差拉回 1 左右，让 softmax 保持在有梯度的区间。

3. 位置编码​​：RoPE 旋转位置编码的原理及实现

    **口语版：**
    RoPE 的核心想法是：不把位置信息"加"到 embedding 上，而是把 Q 和 K 向量按位置"旋转"一个角度。实现上，把 d 维向量两两一组看成 d/2 个二维平面，第 m 个位置的 token 就在每个平面上旋转 m 乘以 θi 的角度，θi 随维度指数递减——高频维度编码近距离，低频维度编码远距离，跟正弦编码的频率设计一个思路。
    它最漂亮的性质是：两个旋转后的向量做点积，结果只取决于角度差，也就是 m 减 n——所以 attention 分数天然只依赖相对位置，不依赖绝对位置。而且不用改 attention 结构，代码上就是对 Q、K 逐元素乘 cos 和 sin。外推性也比加性编码好，配合 NTK、YaRN 这类频率插值方法可以把上下文长度扩展好几倍，这也是 Llama、Qwen 这些主流开源模型都用 RoPE 的原因。

## training

3. ​​微调与对齐​​：PPO、DPO、LoRA 的原理及区别；RLHF 的具体工程流程。

    **口语版：**
    先说 LoRA，它跟前两个不是一类东西。LoRA 是参数高效微调：冻结原模型权重，在权重矩阵旁边加一对低秩矩阵 A 乘 B 来学"增量"，可训练参数量降几个数量级，显存需求也小很多。我在微软的后训练就是 LoRA 做的 SFT 加 RL。
    PPO 和 DPO 都是偏好对齐方法。PPO 是标准 RLHF 里的强化学习算法：先用人标的偏好数据训一个 reward model，然后 policy 采样生成、reward 打分、用 clip 过的目标函数更新 policy，同时用 reference model 算 KL 惩罚防止模型跑偏。工程上很重——要同时维护 policy、reference、reward、value 四个模型。
    DPO 的洞察是这套 RL 流程可以在数学上化简掉：直接拿偏好对做一个对比式的 loss，隐式优化同一个目标。不需要 reward model、不需要在线采样，工程上简单得多；代价是纯离线、没有探索，效果上限一般认为略低于调好的 PPO。
    RLHF 完整流程三步：SFT 打底 → 人标偏好数据训 reward model → PPO 强化学习加 KL 约束。我自己实际跑的是 GRPO，PPO 的简化变体：同一个 prompt 采样一组回答，用组内相对得分当 advantage，省掉了 value model——我们用自定义 reward 让模型在准确率提升 9% 的同时，单查询成本降了 14%。

## AI Agent
1. 请解释Agent的核心架构，它与单纯调用大模型API相比，解决了哪些问题？

    **口语版：**
    Agent 的核心架构就是一个闭环：LLM 拿到目标和上下文 → 决定调用哪个工具 → 执行 → 把结果塞回上下文 → 再推理，循环到它判断任务完成。核心组件四个：决策的 LLM 本身、工具层、记忆和上下文管理、终止判断。
    跟裸调 API 相比解决了三件事。第一，能"行动"了——查网页、跑代码、改文件，不再只是输出文本。第二，能接触实时的、私有的信息，弥补知识截止和幻觉。第三，也是最关键的：一次 API 调用是开环的，错了就错了；Agent 是闭环的，工具的执行结果会反馈回来，模型可以基于观察自我纠错，所以才能做多步的长任务。

2. Function Calling中，如何设计工具描述和参数Schema来提升大模型的调用准确率？

    **口语版：**
    几条实践经验。一，描述里要写清"什么时候该用、什么时候不该用"，而不只是"这工具是干嘛的"——模型选错工具大多是边界没写清。二，参数要少、要扁平，能用枚举就不用自由字符串，嵌套对象是出错重灾区。三，参数名自解释、带单位，比如 timeout_seconds 而不是 timeout。四，描述里放一两个调用示例，few-shot 对准确率提升很明显。五，工具的报错要结构化、模型可读——模型看得懂错误才能自我修正。
    最后一点是别凭感觉迭代：拿一批真实 query 建个小评测集，逐工具看混淆矩阵，哪两个工具老被搞混就改哪两个的描述。

3. 多步任务中Agent陷入循环或偏离目标时，如何设计有效的终止条件与反思机制？

    **口语版：**
    我分硬性兜底和软性反思两层。硬性的：最大步数、token 预算、单工具连续失败上限，以及重复动作检测——连续几次同工具同参数就强制打断。软性的：每隔几步让模型对照原始目标复述"我在哪、还差什么"，并且把计划固化成显式的 todo 列表，靠结构记住而不是靠注意力记住。
    我在微软做多 agent 系统时对这个体会很深：最常见的失败不是死循环，而是"提前收敛"——agent 自己觉得做完了，其实还缺内容。我们的解法是终止前强制过一遍 checklist：重新枚举所有子任务、逐条对照产出，全过了才允许停。另外快到预算时注入提醒，让它优先写出部分结果——一个现在就有的部分答案，比一个永远写不完的完整答案值钱得多。

4. 设计一个支持长期记忆和上下文压缩的Agent记忆模块，核心组件与技术选型有哪些？

    **口语版：**
    我会分三层。短期记忆就是当前对话上下文；工作记忆是结构化的任务状态——todo、中间结论，放的是"结论"不是原始日志；长期记忆放外部存储：向量库做语义检索，KV 存储放用户偏好这类结构化事实。
    压缩上三个手段：一是滚动摘要，上下文超阈值就把旧轮次替换成摘要；二是分级存储——工具的原始返回落盘，上下文里只留摘要加引用，需要时再读回来；三是检索式注入，每轮只把和当前子任务相关的记忆片段拉进 prompt，而不是全量塞入。
    选型上向量库用 pgvector 或 Milvus 都行，摘要用便宜的小模型跑。真正的难点不是选型，是写入策略——"什么值得进长期记忆"必须定义清楚，否则记忆库很快变成垃圾场，检索回来全是噪声。

5. 请描述ReAct模式的工作原理，并举例说明它如何结合推理与行动。

    **口语版：**
    ReAct 就是让模型交替输出"推理"和"行动"：先写一段 thought 分析现在该干嘛，然后发一个 action 调工具，工具返回 observation 拼回上下文，再进入下一轮 thought。关键在闭环：推理让行动有依据，行动的观察又修正下一步推理。
    举个例子，问"某篇论文作者的导师是谁"——thought：我得先找到这篇论文；action：搜索；observation：找到了，作者是某某；thought：那去他的主页找导师信息；action：打开主页……每一步的观察都在改变下一步的计划，这是它和"一次性生成完整计划再执行"的本质区别。
    代价是每步一次 LLM 调用，延迟和 token 开销大。我在 browser-use 项目里的做法是加了个 CodeAct 层，让 agent 直接写代码批量执行确定性的操作，LLM round-trip 减少了 95%——该推理的地方用 ReAct，确定性的批量操作交给代码。

6. 多Agent协作场景下，Agent之间的通信、任务分配和状态同步如何实现？

    **口语版：**
    常见三种模式：中心化的 planner-worker、消息总线 mailbox、共享状态。我在微软的 HDMAS 选的是第三种，可以直接讲实战：所有协调状态放在一个共享 blackboard 文件里，OS 文件锁保护，N 个完全对等的 agent 循环执行"加锁 → 读任务日志 → 认领一个任务 → 解锁 → 执行"。
    任务分配就是抢占式认领，不需要 dispatcher；状态同步就是 append-only 的任务日志本身，谁都能审计；终止靠全体投票。好处是没有单点——单个 agent 的错误不会被放大，下一个读黑板的 agent 会自然纠正它。坏处是锁把"认领"这一步串行化了：我们实测 3 个 agent 最优，8 个 agent 成本翻倍、exact-match 反而下降，因为大家在抢最终答案文件的写权。
    所以我的结论是：任务宽、弱耦合，用去中心化共享状态；强依赖的流水线，用中心化编排——按任务结构选，不是按架构信仰选。

7. Agent调用外部API出现超时或返回异常格式时，如何设计稳健的重试和降级策略？

    **口语版：**
    重试先分错误类型：超时和 429 值得重试，用指数退避加抖动，并设总预算防止无限重试；4xx 参数错误重试没有意义，正确做法是把报错原文塞回上下文，让模型修正参数再调。
    格式异常，我的顺序是：严格 schema 校验 → 失败后做"修复性重试"，把原始输出和报错一起发回去让模型自己修 → 还不行就降级到确定性解析，比如正则抽关键字段。
    降级分三级：工具级——主搜索源挂了切备用源；模型级——大模型超时切小模型；功能级——拿不到完整数据就返回部分结果并明确标注。最后所有失败都要打点：我习惯用 Langfuse 把每步的错误、延迟、重试次数 trace 下来，线上出问题按 request ID 就能回放整条链路。

9. 评估Agent系统的性能，你会关注哪些关键指标？如何收集和监控这些指标？

    **口语版：**
    我分四层。任务层：端到端成功率，而且要同时报严格指标和宽松指标——我在 WideSearch 上就踩过这个坑：细粒度的 Item-F1 在涨，exact-match 反而在跌，只看一个会完全误判系统状态。过程层：平均步数、工具调用成功率、循环卡死率、提前终止率。资源层：单任务 token 成本、延迟，以及"每正确答案的成本"——这比单任务成本诚实得多。质量层：幻觉率、结论可溯源率。
    收集上靠全链路 tracing：我用 Langfuse 给每一步记 token、延迟、错误，按 request ID 回放整条轨迹归因成本。线上再加采样评估——LLM judge 打分加人工抽检，judge 本身要定期校准。最后是回归集：固定一批 case，每次改 prompt 或换模型都跑一遍，防止悄悄变差。

10. 使用LangChain等框架开发Agent时，遇到过哪些架构或性能局限？你是如何绕过的？

    **口语版：**
    我主要的实战是 browser-use 和 AgentScope Runtime，坑是相通的。第一，抽象层太厚：框架把 prompt 拼接和循环逻辑包起来，调试时根本看不到真正发给模型的内容，想改一个细节要翻好几层源码——我的办法是接全链路 tracing，把每个真实请求落盘。第二，逐步循环太慢：browser-use 默认每个动作一次 LLM 调用，我扩展了一个 CodeAct 工具层，让 agent 写 JS 批量操作 DOM，round-trip 降了 95%，任务产出从 1 条提到 14 条。第三，框架之间互不兼容：我在阿里云就是专门做 A2A 协议适配器，用双向 JSON-RPC 翻译解决跨框架互操作。
    总结成一句话：框架适合起步，但上生产必须保住两件事——看得到每一个真实的 LLM 请求，以及能绕过框架直接控制关键路径。

11. Agent需要操作数据库或文件系统，如何防止提示注入导致的越权或误操作？

    **口语版：**
    原则是把 agent 当成不可信用户。第一，最小权限：数据库给只读账号、白名单表；文件系统圈在沙箱目录里；删库这类高危操作干脆不提供工具。第二，指令和数据分离：网页、检索结果这类外部内容进上下文时打标记，告诉模型"这是数据不是指令"——但要清楚这只是缓解，不是保证。第三，也是真正的安全边界：硬校验放在工具层代码里，SQL 只允许参数化模板、文件路径做规范化校验防目录穿越——prompt 里的约束防不住注入，代码里的约束才防得住。第四，高危动作转人工确认，我 browser-use 项目里登录这类敏感环节就是 human-in-the-loop 交给用户自己做的。第五，全程审计日志，出了事能追溯。

12. 为控制延迟和成本，Agent在调用大模型时有哪些优化策略？（如缓存、压缩、模型路由等）

    **口语版：**
    分几个层面。缓存：系统 prompt 和工具定义放在前缀、保持稳定，命中推理侧的 prefix cache；重复问题上语义缓存直接返回。压缩：滚动摘要、工具返回截断落盘、按需注入相关片段。模型路由：简单步骤走小模型，规划和关键决策才用大模型——我在微软后训练 7B 模型就是这个思路的极致：专项任务上 SFT 加 GRPO 之后小模型顶上，每查询成本降 14%、延迟降 9%。减少循环次数：这是最容易被忽略的大头，我用 CodeAct 把十几次工具调用合并成一段代码一次执行，round-trip 省了 95%。再加上独立子任务并行、流式输出改善体感。
    最重要的一条是先测量再优化：用 tracing 把成本按步骤归因，找到真正烧钱的那一步——通常不是你以为的那一步。

13. 给出一段Agent循环调用工具的伪代码，分析可能导致token快速耗尽或死循环的问题点，并给出改进思路。

    **口语版：**
    最朴素的循环就是：`while true → resp = llm(messages) → result = 执行工具(resp) → messages.append(result)`。四个问题点：一，没有终止上限——模型可能永远不输出"完成"，直接死循环；二，工具返回原封不动 append——一个大网页几万 token，上下文很快爆掉，而且旧观察永远不清理；三，没有重复检测——模型很容易卡在"同一工具同一参数"里反复试；四，错误没有分类处理——失败信息原样塞回去，模型可能一直重复同一个失败调用。
    改进对应四条：加最大步数和 token 预算的硬顶；工具返回先截断或摘要再入上下文，原文落盘按需读取；给动作算指纹，检测到重复就注入提醒强制换策略；错误分类——可重试的自动退避重试，不可重试的把原因结构化给模型。最后加一个兜底：预算快用完时注入提醒，让它立刻输出目前最好的部分答案，保证任务不空手而归。

14. 多Agnet架构和单agent多skill架构的区别，分别适合什么

    **口语版：**
    本质区别是上下文和控制权是否隔离。单 agent 多 skill：一个上下文、一个决策循环，skill 只是工具库更丰富。优点是没有协调开销、状态天然一致、便宜、好调试；缺点是长任务下上下文膨胀、注意力漂移。多 agent：每个 agent 独立上下文、独立循环，能并行，还能隔离失败——一个 agent 跑偏不会污染其他人，也可以按 agent 分配不同权限和模型。
    适用上我的经验是：任务串行、强依赖、规模不大，单 agent 多 skill 几乎总是更好，不要为了架构而架构。任务宽而弱耦合、需要并行覆盖、或者失败隔离很重要时，才值得上多 agent。我在 WideSearch 上的实测正好是这个结论的注脚：3 个 agent 比单 agent 好 11% 的相对 Row-F1，但 8 个 agent 成本翻倍效果反降——多 agent 的协调成本是真实的钱，要先算账再上。


### RAG
1. 如何将RAG与Agent结合？当检索结果有噪声时，如何避免干扰Agent的推理与决策？
